## 0. 执行摘要

### 0.1 为什么要做这件事

民航是一个**由多个法人主体在同一物理空间内、按同一时刻表、用互不隶属的 IT 系统协同完成一件事**的行业。一位旅客从家门口到落座机舱，平均触发 **9 类主体、20 余套系统、40 余条标准报文**。行业新人、机场管理培训生、航司地服人员、以及做民航数字化的产品与技术人员，普遍存在三个认知断层：

1. **只见触点、不见系统**：知道值机柜台是干什么的，不知道柜台背后跑的是航司 DCS 而不是机场系统；
2. **只见系统、不见主体**：知道 AODB、DCS 这些缩写，但说不清谁拥有、谁付费、谁在故障时负责；
3. **只见流程、不见层级**：能背出旅客九步流程，却无法把它挂到「航站楼管理 / 飞行区管理 / 地服管理 / 陆侧交通管理」这些**更高一层的管理域**上去。

本项目用一个可交互的 3D 教学模拟器来消除这三个断层：**以旅客第一人称走完全流程为主线（看得见的世界），实时并列展示每一步背后的系统链路与报文（看不见的世界），并在右侧始终显示当前步骤所属的机场管理域与其兄弟域（更高一层的知识地图）**。

### 0.2 本报告的产出

| 部分 | 内容 | 用途 |
|---|---|---|
| 第一部分（第 1–7 章） | 行业洞察：管理理念演进、机场侧系统全景、航司侧系统全景、主体边界、旅客端到端触点解剖、KPI 体系 | Demo 的知识底稿，即右侧知识面板的全部内容来源 |
| 第二部分（第 8–14 章） | Demo 设计：教学目标、交互脚本与分支、3D 场景设计、信息架构、数据契约、技术架构、分步实施计划与验收标准 | 开发施工图，逐步生成 3D Demo 的依据 |

### 0.3 核心洞察（一句话版本）

> **机场卖的是"空间与时间"，航司卖的是"座位与行程"，地服卖的是"工时与设备"；旅客旅程之所以复杂，是因为这三种商品在同一条流水线上被同时消费，而它们各自的 IT 系统被各自的商业模式塑形——理解了谁的系统在什么时候接管旅客，就理解了民航运行的绝大部分。**

# 第一部分：行业洞察

## 1. 现代机场管理理念的演进

### 1.1 三个阶段

| 阶段 | 时期 | 管理范式 | 典型特征 | 代表机制 |
|---|---|---|---|---|
| **阶段一：分立运行** | 1990s 之前 | 部门孤岛（Silo） | 塔台管跑道、航站楼管闸口、地服管拖车，各自排班、各自记录，靠电话与对讲机协同 | 纸质工作单、电话协调 |
| **阶段二：协同决策** | 2000s–2010s | A-CDM（Airport Collaborative Decision Making，机场协同决策） | 机场、航司、地服、空管**共享同一份时间戳数据**，把"过站"从黑箱变成 16 个可测量里程碑 | EUROCONTROL A-CDM 规范、TOBT/TSAT |
| **阶段三：全面机场管理** | 2010s–至今 | **TAM（Total Airport Management，全面机场管理）** | 把 A-CDM 的范围从"停机坪"扩展到**陆侧 + 空侧 + 网络**，用一份滚动的机场运行计划（AOP）驱动一个实体化的机场运行控制中心（APOC） | SESAR PJ04 TAM、AOP/NOP 对接、SWIM |

### 1.2 A-CDM：现代机场运行的地基

A-CDM 的本质是一个**共享时间戳协议**。它让所有参与方对"这架飞机现在到底处在什么状态"达成唯一共识，从而把主观的"差不多快好了"变成客观的可预测数字。

**16 个里程碑（Milestones）**——欧洲版本的标准序列：

| # | 里程碑 | 关键时间戳 | 谁产生 |
|---|---|---|---|
| MS1 | ATC 飞行计划激活（EOBT−3h） | EOBT | 空管/航司 |
| MS2 | EOBT−2h，进港航班确认 | — | 空管 |
| MS3 | 前站起飞 | ATOT(前站) | 前站 |
| MS4 | 本场雷达首次更新 | ELDT 更新 | 空管 |
| MS5 | 最后进近 | ELDT | 空管 |
| MS6 | **落地** | **ALDT**（Actual Landing Time） | 空管 |
| MS7 | **上轮档 / 入位** | **AIBT**（Actual In-Block Time） | 机场/地服/VDGS |
| MS8 | 地面保障开始 | AGHT 起点 | 地服 |
| MS9 | **TOBT 更新** | **TOBT**（Target Off-Block Time，目标撤轮档时间） | **航司/地服**（谁负责保障谁报） |
| MS10 | **TSAT 下发** | **TSAT**（Target Start-up Approval Time，目标开车许可时间） | 空管/CDM 平台 |
| MS11 | 开始登机 | — | 航司/地服 |
| MS12 | 航空器就绪 | — | 机组/地服 |
| MS13 | 申请开车 | — | 机组 |
| MS14 | 批准开车 | ASAT | 空管 |
| MS15 | **撤轮档** | **AOBT**（Actual Off-Block Time） | 地服/机场 |
| MS16 | **起飞** | **ATOT**（Actual Take-Off Time） | 空管 |

**教学要点（Demo 中会用到）**：
- **TOBT 是航司/地服的承诺，TSAT 是空管的排队号**。旅客感受到的"为什么登机完了还不走"，很多时候是 TSAT 尚未到达，飞机在机位上"带客等待"——这是为了节油和减少滑行道拥堵而**有意为之**的设计，不是失误。
- **SOBT/STD（计划）→ EOBT（估计）→ TOBT（目标）→ TSAT（放行）→ AOBT（实际）** 这条时间链，是理解全部离港管理的钥匙。

### 1.3 TAM：从停机坪走向"整个机场"

TAM 是 SESAR（欧洲单一天空空管研究计划）在 A-CDM 之上提出的下一代概念，其 PJ04 项目（2016-12 至 2019-12）产出了可规模化的运行概念与逻辑架构。两个核心构件：

- **AOP（Airport Operations Plan，机场运行计划）**：一份**滚动的、共享的、覆盖未来 24–72 小时的**机场运行意图，包含航班、机位、值机柜台、安检通道、行李分拣口、人力与设备、旅客量预测、天气与容量约束。它是"机场版本的飞行计划"。
- **APOC（Airport Operations Centre，机场运行控制中心）**：AOP 的执行与决策实体。物理上是一个大厅，逻辑上是所有管理域（陆侧、航站楼、飞行区、地服、安保、商业）代表**同桌办公 + 同屏看板**。

TAM 与 A-CDM 的关键差异：
1. **范围**：A-CDM 从落地到起飞；TAM 从旅客离家到旅客离场（curb-to-curb），含陆侧交通与商业。
2. **对象**：A-CDM 管航班；TAM 同时管**旅客流**与**航班流**。
3. **网络**：TAM 通过 SWIM（System Wide Information Management，全域信息管理）把本场 AOP 与欧洲网络运行计划 NOP 双向对接——本场机位不够时，网络侧可提前调整流量。

### 1.4 中国语境：智慧民航与"四型机场"

中国民航局《智慧民航建设路线图》（民航发〔2022〕1 号）与《四型机场建设行动纲要（2020—2035 年）》确立了 **"平安、绿色、智慧、人文"四型机场**框架。落到旅客旅程上，最具体的抓手是：

- **无纸化便捷出行 / "一码通行"**：电子登机牌 + 身份证/人脸作为唯一凭证，贯穿安检、候机、登机；
- **全流程人脸识别**：值机、行李托运、安检、登机的多点生物识别；
- **RFID 行李全流程跟踪**：对应 IATA Resolution 753 的国内实现；
- **中国航信（TravelSky）的角色**：作为国内绝大多数航司的 PSS 提供方（含 ICS 订座/Inventory 与**离港系统 DCS**）以及机场端多套系统的供应商，形成了与欧美（Amadeus/Sabre 双寡头 + 机场系统多供应商）不同的**高度集中**的产业格局。

**教学要点**：同一个"值机柜台"，在法兰克福背后可能是 Amadeus Altéa DCS，在北京背后大概率是中国航信离港系统——**设备是机场的，系统是航司的，这一条在全球通用**。

### 1.5 数据驱动层：DSS、BI 与数字孪生

- **DSS（Decision Support System，决策支持系统）**：在民航语境里通常指 APOC 内的"what-if"推演工具——如"若 3 号跑道关闭 40 分钟，未来 2 小时机位与行李分拣口如何重排"。
- **BI / 数据中台**：把 AODB、DCS、BHS、安检、停车等系统的历史数据汇聚，产出 OTP、TAT、ASQ、单位旅客能耗等指标。
- **数字孪生（Digital Twin）**：把 DSS 与 BI 可视化并接入实时数据，形成"看得见的机场"。当前业界实践集中在三类：航站楼旅客流仿真、机坪/过站 AI 视觉分析（如 Assaia 对 45 万+ 次过站的分析显示，AI 过站可视化可使离港延误显著下降）、以及全场态势的三维可视化。
- **AI 预测**：安检排队拥堵提前 15–20 分钟预警、过站超时预警、行李分拣口溢出预警，是当前落地最多的三个预测场景。

## 2. 机场侧系统全景

机场侧 IT 可分为**六层**。理解这六层的归属，是理解"机场到底管什么"的捷径。

### 2.1 运行核心层（Operations Core）

| 系统 | 全称 | 作用 | 与旅客旅程的关系 |
|---|---|---|---|
| **AODB** | Airport Operational Database，机场运行数据库 | **全场航班数据的唯一真源**。汇聚航季计划（SSIM）、当日动态、机位/廊桥/值机柜台/行李转盘分配、实际时间戳，并向下游所有系统分发 | 旅客看到的每一块屏幕上的航班号、登机口、行李转盘号，源头都在这里 |
| **RMS / AMS** | Resource Management System / Airport Management System，资源管理系统 | 分配"有限的物理资源"：机位、廊桥、值机柜台、登机口、行李提取转盘、行李分拣口、摆渡车 | 决定了旅客"去哪个柜台、走哪个登机口" |
| **FIDS** | Flight Information Display System，航班信息显示系统 | 把 AODB 数据渲染到航显屏、广播、App、网站；通常经 **AIDX**（IATA 航班数据交换 XML 标准）与外部交换 | 旅客最直接的信息界面 |
| **A-CDM 平台** | — | 计算与发布 TOBT/TSAT/TTOT，驱动 16 里程碑 | 决定航班何时被允许推出 |
| **APOC 看板 / DSS** | — | 全域态势与推演 | 幕后 |
| **计费系统** | Billing | 起降费、停场费、廊桥费、旅客服务费、柜台使用费 | 幕后（但决定机场收入） |

**关键认知**：**AODB 是机场的"心脏"，但它不含旅客个人数据**。旅客姓名、护照号、座位、行李归属，全部在**航司 DCS** 里。机场只知道"CA1501 有 168 人值机、23 件托运行李"，不知道"张三坐 12A"。这条边界由数据保护法规与商业分工共同划定。

### 2.2 旅客处理层（Passenger Processing）

| 系统/设备 | 说明 | 归属 |
|---|---|---|
| **CUTE → CUPPS** | Common Use Terminal Equipment → Common Use Passenger Processing Systems（共用旅客处理系统，IATA RP 1797）。让**一台机场的柜台设备**能按需登录**任意一家航司的 DCS** | 硬件与平台是机场的；上面跑的应用是航司的 |
| **CUSS** | Common Use Self Service，共用自助值机终端（Kiosk） | 同上 |
| **SBD** | Self Bag Drop，自助行李托运（分一步式 one-step 与两步式 two-step） | 同上 |
| **CUPPS 云化** | 如 Amadeus ACUS（Amadeus Common Use Service）等云共用平台 | 机场采购的云服务 |
| **安检信息系统** | 通道排队、开放通道数、旅客核验（含人证核验闸机） | 机场/安检机构 |
| **BGR** | Boarding Gate Reader，登机口读码器 | 设备机场、系统航司 |
| **旅客流量测量** | Wi-Fi/BLE 探针、摄像头计数、排队时间预测 | 机场 |

**这是全报告最重要的一条边界**：
> **值机柜台/自助机是机场提供的"共用设备"（CUPPS/CUSS），你在上面办理的业务跑在航空公司的 DCS 上。** 这就是为什么同一台机器，前一小时给国航用、后一小时给东航用，界面完全不同。

### 2.3 行李层（Baggage）

| 系统 | 全称 | 作用 |
|---|---|---|
| **BHS** | Baggage Handling System，行李处理系统 | 物理传送带、分拣机、安检机（HBS）、分拣口（Make-up）、提取转盘。**机场资产** |
| **BRS** | Baggage Reconciliation System，行李核对系统 | 逐件跟踪行李，确保"人走行李走、人不走行李不走"（Bag-Passenger Reconciliation），是安保刚需 |
| **HBS** | Hold Baggage Screening，托运行李安检 | EDS/CT 断层扫描，多级（Level 1–5）分流 |
| **ATR** | Automatic Tag Reader，自动读码器 | 读行李条 LPN（License Plate Number，10 位行李牌号） |

**IATA Resolution 753（行李跟踪决议）**要求承运人在四个节点获取并保存行李状态证据：**① 接收（值机/托运）② 装机 ③ 中转交接 ④ 到达交付**。

**核心报文（IATA Type B 报文族）**：

| 报文 | 全称 | 方向 | 含义 |
|---|---|---|---|
| **BSM** | Baggage Source Message | DCS → BHS/BRS | "我刚收了一件行李，牌号 0999123456，属于旅客 X，航班 CA1501" —— **行李在数字世界诞生的时刻** |
| **BPM** | Baggage Processed Message | BHS/BRS → DCS | "这件行李已过安检 / 已到分拣口 / 已装机" |
| **BTM** | Baggage Transfer Message | 前站 → 后站 | 中转行李预告 |
| **BUM** | Baggage Unload Message | DCS → BHS | "旅客未登机，把这件行李找出来卸下" |
| **BNS** | Baggage Not Seen | BHS → DCS | "这件行李在预期节点没出现" |

**教学要点**：旅客把箱子放上传送带的一瞬间，发生的不是"箱子被运走"，而是**一条 BSM 报文让这件行李在系统里获得身份**。此后每一次扫描都在这条身份上追加一个 BPM。IATA 753 的四个节点、行李找回、以及"旅客没登机必须卸行李"的安保规则，全部建立在这条数据链上。

### 2.4 飞行区层（Airside）

| 系统 | 说明 |
|---|---|
| **A-SMGCS** | Advanced Surface Movement Guidance & Control System，先进场面活动引导与控制系统（场面雷达 + 多点定位 + 冲突告警） |
| **VDGS** | Visual Docking Guidance System，目视泊位引导系统（机头前的那块屏），同时是 **AIBT 时间戳的主要自动来源** |
| **ALCMS** | 助航灯光控制与监控系统 |
| **除冰管理 / 跑道状况（RCR）/ 鸟击防范（Wildlife）/ 应急救援（ARFF）** | 飞行区安全域 |
| **机坪塔台 / 机位分配** | 由机场或空管运营，取决于国家体制 |

### 2.5 地面服务层（Ground Handling）

| 系统 | 说明 | 代表产品 |
|---|---|---|
| **地服资源管理** | 人员排班、资质匹配、GSE（地面保障设备）调度、实时任务派发 | INFORM GroundStar 等 |
| **过站管理（TMS）** | 13–20 个保障节点的计划/实际时间、超时预警 | Assaia TurnaroundControl 等 AI 视觉方案 |
| **GSE 管理** | 电动化、位置、油耗、碰撞检测 | — |
| **配载（Load Control）** | 见 3.2，**这是航司职责，常委托地服执行** | — |

### 2.6 陆侧与支撑层（Landside & Enabling）

| 域 | 系统 |
|---|---|
| **陆侧交通** | 停车管理、车牌识别（ANPR）、路侧（Curbside）占用与滞留监测、网约车/出租车池调度、APM（旅客捷运）、轨道/机场巴士接口 |
| **商业** | 零售租金与提成、免税、餐饮、广告、旅客消费画像 |
| **安保** | CCTV、门禁（ACS）、周界、员工背景审查 |
| **设施** | BIM/FM 资产管理、能源（含 FEGP 400Hz 与 PCA 桥载空调）、暖通、电梯 |
| **网络与信息安全** | 机场是关键信息基础设施，CUPPS/BHS/A-SMGCS 均为高价值攻击面 |

## 3. 航空公司侧系统全景

### 3.1 PSS：航司的"三件套"

**PSS（Passenger Service System，旅客服务系统）** 是航司最核心的 IT 资产，通常由三个模块构成：

| 模块 | 作用 | 关键概念 |
|---|---|---|
| **RES（Reservation，订座）** | 创建与维护 **PNR**（Passenger Name Record，旅客订座记录）；处理改期、退票、特殊服务 | PNR、SSR（特殊服务请求）、电子客票 ET |
| **INV（Inventory，运力/舱位）** | 管理"哪个航班、哪个舱位、还剩几个座位、卖多少钱"；与收益管理（RM）联动 | 舱位等级、超售（Overbooking）、AVS/AVN |
| **DCS（Departure Control System，离港控制系统）** | 从值机开放到航班关闭的全部地面动作 | 见 3.2 |

**主流供应商**：Amadeus **Altéa**（Altéa Reservation / Altéa Inventory / Altéa Departure Control）、Sabre **SabreSonic**、中国航信 **TravelSky**（ICS + 离港系统）、以及 Hitit Crane、Radixx 等中小型方案。低成本航司也可能采用轻量 PSS 或自研。

### 3.2 DCS 深挖：两个"半边"

Amadeus 的产品划分很好地揭示了 DCS 的内部结构，业界通用：

**（A）DCS-CM（Customer Management，客户管理侧）——面向旅客**
- 值机（Check-in）：柜台、Kiosk、Web/App、自助托运
- 座位分配（Seat Map）
- 行李接收（Bag Acceptance）→ 产生 **BSM**
- 证件与签证核验（TIMATIC 类规则库）
- 常旅客识别、升舱、付费选座与行李
- 登机（Boarding）：扫码核验、登机人数统计
- 联程与联运值机（Through / Interline Check-in）

**（B）DCS-FM（Flight Management，航班管理侧）——面向航空器**
- **配载平衡（Weight & Balance / Load Control）**：计算重心（CG）、配平、载重表（Loadsheet），**关系飞行安全，法定由航司放行人员签署**
- 舱单与载量分配（客/货/邮/行李在各货舱的分布）
- 生成 **LDM**（Load Message，载重报）、**CPM**（Container/Pallet Distribution Message，集装箱分布报）、**UCM**（ULD Control Message）
- **MVT**（Movement Message，动态报）：AD（撤轮档）/ AA（上轮档）时间

### 3.3 DCS 的上下游接口（Demo 的数据流骨架）

```
【值机开放前】
  RES/INV ──PNL（Passenger Name List，旅客名单）──▶ DCS
  RES/INV ──ADL（Addition & Deletion List，增删表，增量刷新）──▶ DCS
  RES     ──PSM（Passenger Service Message，特殊服务）──▶ DCS
【值机过程中】
  DCS ──BSM──▶ BHS/BRS            （行李诞生）
  DCS ◀──BPM── BHS/BRS            （行李过点）
  DCS ──旅客数/行李数/登机口──▶ AODB ──▶ FIDS/RMS   （经 AIDX）
  DCS ──API/APIS/PNRGOV──▶ 边检/海关/移民局        （法定预报）
  DCS ◀──▶ 常旅客/CRM、付费选座与行李（辅营）
【航班关闭后】
  DCS ──Loadsheet / LDM / CPM──▶ 机组、目的站、地服
  DCS ──PFS（Passenger Final Sales，最终销售报）──▶ RES/INV
  DCS ──实际旅客数──▶ 收入结算（Revenue Accounting）与 BSS
  DCS ──MVT（AD/AA）──▶ 全网、AODB、A-CDM
```

### 3.4 术语澄清：BSS 到底是什么

用户与业界常混用的 "BSS" 有两种含义，必须区分（本 Demo 会显式标注）：

| 缩写 | 语境 | 含义 |
|---|---|---|
| **BSS** | 航司/电信 IT | **Business Support System，商务支撑系统**：收入结算（Revenue Accounting）、财务、清算（BSP/ICH/ACH）、辅营计费。DCS 关闭航班后把实际承运数据交给它 |
| **BHS** | 机场 | Baggage Handling System，行李**物理**处理系统 |
| **BRS** | 机场/航司 | Baggage Reconciliation System，行李**数据**核对系统 |
| **BSM** | 报文 | Baggage Source Message，行李源报文 |

### 3.5 航司的其他关键系统

| 系统 | 作用 |
|---|---|
| **AOC / OCC（运行控制中心）** | 航班监控、放行、不正常航班处置（延误、取消、备降、调机） |
| **Flight Planning / 签派** | 航路、油量、备降场、性能计算 |
| **Crew Management** | 机组排班与资质、法定休息（FTL） |
| **MRO / MCC** | 机务与维修控制 |
| **Loyalty / CRM** | 常旅客与客户画像 |
| **NDC / ONE Order** | IATA 现代零售标准：以 **Offer（报价）+ Order（订单）** 取代传统 PNR/ET/EMD 的多凭证结构 |
| **EFB** | 电子飞行包，接收 Loadsheet 与性能数据 |

### 3.6 生物识别与数字身份（IATA One ID）

**One ID** 的目标是让旅客**只验证一次身份**，此后在各触点用生物特征"刷脸通过"，无需反复出示护照与登机牌。到 2026 年，行业口径为 500+ 机场至少部署一个生物识别触点、120+ 具备端到端数字身份走廊。技术实现上正与**可验证凭证（Verifiable Credentials）**、数字旅行凭证（DTC）结合。

**对旅客旅程的改变**：值机、托运、安检、边检、登机五个触点的"证件核验"动作被统一为一次远程注册 + 多次本地比对，**但背后的 DCS/BRS/边检系统依然存在**——变的是界面，不变的是数据链。这一点在教学中极易被误解，Demo 会专门用一个开关演示"传统模式 vs One ID 模式"的对比。

## 4. 主体边界：谁拥有什么、谁为什么付费

| 主体 | 核心资产 | 核心系统 | 收入来源 | 在旅客旅程中的接管时段 |
|---|---|---|---|---|
| **机场** | 空间、设施、时刻 | AODB、RMS、FIDS、BHS、CUPPS/CUSS、安检信息系统 | 航空性收入（起降/停场/旅客服务费）+ 非航收入（零售/停车/租金） | 进入红线到登机口，全程提供"场地与设备" |
| **航空公司** | 座位、航权、机队、品牌 | PSS（RES/INV/DCS）、AOC、Loyalty、BSS | 客票 + 辅营（选座/行李/餐食） | 值机 → 登机 → 承运，全程拥有"旅客数据" |
| **地面服务代理** | 人力、GSE | 地服资源管理、过站管理，**登录航司 DCS 作业** | 按架次/按服务项收费 | 值机柜台、行李、机坪保障（常代表航司执行） |
| **空管（ATC/ATM）** | 空域与跑道容量 | 塔台系统、A-SMGCS、流量管理 | 空管费 | 滑行、起降 |
| **政府机构** | 法定权力 | 边检（e-Gate、EES/ETIAS）、海关、安检监管 | 财政 | 安检、边检、海关 |
| **商业租户** | 品牌与商品 | POS、库存 | 销售 | 候机区停留时段 |
| **陆侧交通运营方** | 车辆、轨道 | 排班、票务 | 票款 | 到达机场前 |

**教学要点**：旅客体验到的"一次旅行"，在管理上是**七套 KPI、七本账**。绝大多数体验断点（等待、信息不一致、行李错运）都发生在**主体交接处**，这正是 A-CDM 与 TAM 试图缝合的地方。

## 5. 旅客端到端触点解剖（Demo 主线的知识底稿）

以下 10 个触点即 Demo 的 10 个关卡。每个触点统一按 **旅客动作 / 前台设备（谁的）/ 后台系统（谁的）/ 数据与报文 / 所属管理域 / KPI / 典型异常** 六要素解剖。

### 触点 1：公共交通到机场（Landside Access）

- **旅客动作**：乘地铁/机场巴士/网约车/自驾抵达
- **前台设备**：轨道闸机、巴士站台、路侧落客区（Curbside）、停车场道闸（**机场 + 交通运营方**）
- **后台系统**：停车管理系统、ANPR 车牌识别、路侧占用监测、APM 调度、交通信息发布屏；**旅客量预测模型**（把航班时刻表 → 反推到达曲线）
- **数据流**：航班时刻（AODB）→ 陆侧到达量预测 → 路侧/停车/巴士频次调度
- **所属管理域**：**陆侧交通管理（Landside / Ground Transportation）**
- **KPI**：路侧平均滞留时长、停车周转率、公共交通分担率、门到门时间
- **典型异常**：早高峰路侧堵塞（原因常是"停车滞留"而非"车流量"）；末班地铁与红眼航班不匹配

### 触点 2：进入航站楼与寻路（Terminal Entry & Wayfinding）

- **旅客动作**：进门、看航显、找值机岛
- **前台设备**：航显屏（FIDS）、导向标识、问询、安检前人证核验（部分国家）
- **后台系统**：**FIDS ← AODB**；旅客流量测量；广播（PA）
- **数据流**：AODB 的值机柜台分配（RMS 产出）→ FIDS 显示"CA1501 → 值机岛 D"
- **所属管理域**：**航站楼管理（Terminal Operations）**
- **KPI**：寻路成功率、航显准确率与刷新时延
- **典型异常**：柜台临时调整未同步到航显（AODB→FIDS 链路时延）

### 触点 3：值机（Check-in）—— **首个分支点**

- **旅客动作**：三选一 —— ① 手机/网上值机（提前 24–48h）② 自助值机机 Kiosk ③ 人工柜台
- **前台设备**：**机场的 CUSS 自助机 / CUPPS 柜台工作站**（共用设备）
- **后台系统**：**航空公司的 DCS**（如 Amadeus Altéa DC、TravelSky 离港系统）
- **数据与报文**：
  - 值机开放前：INV/RES → **PNL** → DCS；随后持续 **ADL** 增量刷新
  - 值机时：DCS 校验 ET（电子客票）状态、证件与签证规则、座位图、常旅客
  - 值机后：DCS → **API/APIS**（法定旅客预报）→ 边检；DCS → AODB（值机人数）→ FIDS
- **所属管理域**：**旅客服务与航站楼管理**（设备）+ **航司商务运行**（系统）
- **KPI**：自助率（Self-service rate）、平均值机时长、柜台排队时间
- **典型异常**：证件不符（TIMATIC 拒绝）、超售、无座位可选、Kiosk 无法出登机牌需转柜台
- **Demo 分支效果**：
  - **手机值机**：旅程直接跳到"托运/安检"，右侧展示"航司直连 DCS，机场设备零占用"
  - **Kiosk**：展示 CUSS 登录 → 加载航司应用 → DCS 交互 → 打印登机牌与行李牌
  - **柜台**：展示 CUPPS 工作站 + 人工介入场景（特殊服务、超规行李、改签）

### 触点 4：行李托运（Bag Drop）—— **第二个分支点**

- **旅客动作**：二选一 —— ① 自助托运（Self Bag Drop）② 柜台托运
- **前台设备**：自助托运机（含称重、量方、条码/RFID 读取、传送门）或人工柜台传送带
- **后台系统**：**航司 DCS**（接收行李、生成行李牌 LPN）→ **机场 BHS/BRS**
- **数据与报文**：
  1. DCS 接收行李 → 生成 **LPN（10 位行李牌号）**
  2. DCS → **BSM** → BHS/BRS（行李身份诞生，Res 753 节点①"接收"）
  3. 行李进入 BHS：ATR 读码 → 分拣决策 → **HBS 安检**（未通过则人工开包）
  4. 每个节点 BHS → **BPM** → DCS/BRS
  5. 到达分拣口（Make-up）→ 装 ULD/行李车 → 装机（Res 753 节点②"装机"）
- **所属管理域**：**行李管理（Baggage Operations）** + 地服 + 安检
- **KPI**：**MBR（Mishandled Bag Rate，行李错运率，行业以每千名旅客计）**、行李最短接续时间（MCT）、分拣口溢出次数、Res 753 四节点覆盖率
- **典型异常**：超重超规（转特殊行李通道）、安检不通过（旅客被叫回开包）、旅客最终未登机（触发 **BUM** 卸包，全机延误）
- **Demo 分支效果**：
  - **自助托运**：3D 展示"扫登机牌 → 放包 → 自动打牌 → 传送门关闭"，右侧同步弹出 BSM 报文卡片
  - **柜台托运**：3D 展示"人工称重 → 检查超规 → 贴牌 → 上传送带"，右侧额外展示"特殊行李（超长/易碎/危险品）判定规则"分支

### 触点 5：安检（Security Screening）

- **旅客动作**：出示登机牌与证件 → 分拣随身物品 → 过安检门/CT
- **前台设备**：人证核验闸机、ATRS 自动回筐系统、CT/X 光机、金属探测门、毫米波
- **后台系统**：安检信息系统（通道开放数、排队预测）、与 DCS 的登机牌核验接口、监管数据上报
- **所属管理域**：**安全检查 / 安保管理（Security）**，通常由政府或授权机构负责，机场提供场地与排队管理
- **KPI**：平均与 95 分位排队时长、单通道旅客吞吐（pax/hour/lane）、开箱率
- **典型异常**：高峰通道不足、旅客携带违禁品、系统性拥堵（此处是 AI 预测最成熟的场景）

### 触点 6：边检与海关（Border Control）—— 国际航班

- **旅客动作**：护照查验 / e-Gate 自助
- **后台系统**：边检系统、**API/APIS 与 PNRGOV**（航司 DCS 在离港前法定推送）、生物特征库；欧洲已上线 **EES（出入境记录系统）**，**ETIAS** 后续推进
- **所属管理域**：**政府监管域**（机场协同）
- **KPI**：查验时长、e-Gate 使用率、拒登率
- **典型异常**：签证/证件不符导致拒绝登机（**成本由航司承担，故 DCS 在值机时就要预判**）

### 触点 7：候机与商业（Dwell & Retail）

- **旅客动作**：休息、购物、餐饮、贵宾室
- **后台系统**：商业 POS 与租金分成、旅客流量分析、精准营销、登机口变更推送
- **所属管理域**：**商业管理（Commercial / Non-aeronautical）** —— 这是机场利润的主要来源
- **KPI**：人均消费（Spend per pax）、坪效、停留时长（Dwell time）
- **教学要点**：**缩短安检排队 = 延长可消费停留时间**，这是"体验改善"与"商业收入"少见的正向对齐点，也是机场愿意为安检智能化付费的商业逻辑。

### 触点 8：登机口与登机（Gate & Boarding）

- **旅客动作**：到达登机口 → 排队 → 扫码登机
- **前台设备**：**BGR 登机口读码器 / 自助登机闸机 / 人脸识别登机门**（机场设备）
- **后台系统**：**航司 DCS 登机模块**（实时统计已登机人数）→ 与 **BRS** 核对"人包一致"
- **数据流**：
  - 登机开始 → **A-CDM MS11**
  - 未登机旅客（No-show）→ DCS 触发 **BUM** → BHS 找包卸包
  - 登机结束 → DCS 关闭航班 → 生成最终 **Loadsheet** → 发 **LDM/CPM** → 机组签收
- **所属管理域**：**航站楼管理（登机口资源）+ 地服（登机口服务）+ 航司（放行）**
- **KPI**：登机时长、登机口准点开放率、No-show 卸包耗时
- **典型异常**：登机口临时变更（RMS 重排）、旅客失联（Passenger paging）、卸包导致延误

### 触点 9：廊桥/摆渡上机（Boarding Bridge / Bus Gate）

- **旅客动作**：走廊桥或坐摆渡车登机
- **前台设备**：登机桥（含 PCA 桥载空调、FEGP 400Hz 电源）、摆渡车
- **后台系统**：廊桥控制与状态回传 AODB、地服调度、VDGS
- **所属管理域**：**飞行区管理（Airside）+ 地服管理**
- **KPI**：廊桥使用率（vs 远机位比例）、摆渡接驳时长、桥载能源替代 APU 的减排量
- **教学要点**：**远机位不是"低配"，而是机位资源紧张时的容量手段**；桥载电源与空调替代飞机 APU，是机场碳减排的主力项之一。

### 触点 10：关门、推出与起飞（Turnaround Completion）

- **旅客动作**：落座（旅客旅程在此结束，运行旅程继续）
- **系统链**：
  - 客舱关门 → 地服撤桥 → **AOBT（MS15）**
  - 机组按 **TSAT** 申请开车（MS13/14）
  - 推出、滑行、排队、起飞 **ATOT（MS16）**
  - DCS 发 **MVT（AD）**，通知目的站与全网
- **所属管理域**：**飞行区管理 + 空管 + 航司运控**
- **KPI**：**OTP（准点率，通常以 D0/D15 计）**、TAT（Turnaround Time，过站时间）、滑行时间、TOBT 准确度
- **教学要点**：旅客抱怨的"关门后还等了 25 分钟"，通常是 **TSAT 排队**——把等待放在机位（发动机不转）而非滑行道，全网油耗与排放更低。

## 7. KPI 与标准索引

### 7.1 三类主体的核心 KPI

| 主体 | KPI | 定义要点 |
|---|---|---|
| 机场 | ASQ（Airport Service Quality，ACI 旅客满意度） | 问卷驱动，含排队、清洁、寻路 |
| 机场 | 安检排队时长（均值 / 95 分位） | 95 分位比均值更能反映体验 |
| 机场 | 人均非航收入 | 与停留时长强相关 |
| 航司 | **OTP（D0/D15）** | 撤轮档时间 vs 计划撤轮档时间 |
| 航司 | **MBR（行李错运率）** | 每千名旅客的错运件数 |
| 航司 | 座公里成本 / 客座率 | 商务侧 |
| 地服/联合 | **TAT（过站时间）** | AIBT → AOBT |
| 联合 | **TOBT 准确度** | TOBT 与 AOBT 的偏差分布，A-CDM 健康度的第一指标 |
| 联合 | 滑行时间（Taxi-out/in） | 与 TSAT 计量策略强相关 |

### 7.2 标准与规范索引

| 标准 | 领域 |
|---|---|
| IATA Resolution 753 | 行李四节点跟踪 |
| IATA Type B 报文（PNL/ADL/PFS/PSM/BSM/BPM/BTM/BUM/LDM/CPM/UCM/MVT） | 系统间报文 |

# 第二部分：3D 交互教学 Demo 设计

## 8. 产品定义

### 8.1 一句话定义

**《旅客旅程学习模拟器》（Passenger Journey Simulator）**：一个浏览器内运行的 3D 交互教学 Demo，让学习者以旅客第一人称走完"从公共交通到落座"的全流程，每一步同时看到 **① 物理世界发生了什么（3D 场景）② 数字世界发生了什么（系统与报文链路）③ 这一步属于哪个管理域、旁边还有哪些管理域（知识地图）**。

### 8.2 目标用户与教学目标

| 用户 | 教学目标 |
|---|---|
| 机场/航司新员工与管理培训生 | 建立全流程与主体边界的心智模型 |
| 民航数字化产品经理/开发者 | 掌握系统间接口与报文语义，知道改一个字段会影响谁 |
| 高校交通运输/航空管理专业学生 | 把课本概念（A-CDM、AODB、PSS）对应到具体触点 |
| 对民航好奇的公众 | 理解"为什么关门后还要等"这类日常疑问 |

**可测量的学习成果**：完成一次完整旅程后，学习者应能回答：
1. 值机自助机是谁的设备、跑谁的系统？
2. 行李在系统里是什么时候"出生"的？靠哪条报文？
3. 旅客没登机为什么必须卸行李？哪条报文触发？
4. TOBT 和 TSAT 谁定的？为什么关门后还要等？
5. 除了我走过的这条线，机场还并列管着哪 7 个域？

### 8.3 设计原则

1. **双世界并置**：物理（3D）与数字（系统链路）永远同屏，不切页面。
2. **分支即教学**：每个分支点（值机三选一、托运二选一）产生**可见的不同系统链路**，让"选择的后果"成为知识。
3. **纵深可选**：默认展示"够用"的信息；点击任意系统/报文卡片可展开到专家级细节（报文字段、供应商、标准编号）。
4. **上下层贯通**：右侧永远回答"我现在在哪个管理域，它上面是什么，旁边是什么"。
5. **零依赖可离线**：纯前端（Three.js ESM + CDN importmap），无后端，可打包分发。
6. **中英双语**：遵循 OPC Studio 站点标准 i18n 方案（共享 `opcstudio_lang`）。

## 9. 交互脚本与分支设计

### 9.1 主线：10 幕

| 幕 | 场景 | 3D 关键动作 | 分支 |
|---|---|---|---|
| S1 | 地铁站/机场巴士 → 到达 | 列车进站、旅客下车走向航站楼；路侧车流 | 交通方式三选一（地铁/巴士/网约车）—— 影响到达时间与陆侧知识卡 |
| S2 | 航站楼入口与航显 | 抬头看 FIDS 屏，屏上高亮本人航班 | 无（教学节点：AODB→FIDS） |
| S3 | **值机** | 走向值机岛 | **三分支**：手机值机 / Kiosk 自助 / 人工柜台 |
| S4 | **行李托运** | 拖箱到托运点 | **二分支**：自助托运 / 柜台托运；隐藏分支：超规行李 |
| S5 | 行李在幕后（BHS 剖面） | 镜头切到传送带剖面，跟随行李过 ATR → HBS → 分拣口 | 事件分支：安检不通过 → 开包 |
| S6 | 安检 | 排队、放筐、过 CT | 事件分支：随机开包 |
| S7 | 边检（国际） | e-Gate 刷脸 | 开关：国内/国际航班 |
| S8 | 候机与商业 | 在候机区停留、商铺高亮 | 教学节点：停留时长 vs 人均消费 |
| S9 | **登机口** | 扫登机牌、闸机开启 | 事件分支：旅客 No-show → BUM 卸包动画 |
| S10 | 廊桥/摆渡上机 → 关门推出 | 走廊桥进机舱；镜头拉远看撤桥、推出、TSAT 等待 | 分支：近机位廊桥 / 远机位摆渡 |

### 9.2 全局开关（影响多幕）

| 开关 | 取值 | 教学意图 |
|---|---|---|
| 航班性质 | 国内 / 国际 | 国际增加 S7 边检与 API/PNRGOV 报文 |
| 身份模式 | 传统证件 / **One ID 生物识别** | 对比两种模式下各触点的核验动作与数据链变化 |
| 运行态势 | 正常 / 高峰拥堵 / 不正常（延误） | 展示 RMS 重排、TSAT 拉长、行李溢出等管理动作 |
| 视角 | 旅客视角 / 管理者视角（APOC） | 管理者视角切到全场俯视 + AOP 指标条 |

### 9.3 分支的系统链路差异（Demo 的核心教学价值）

**值机三分支对比**

| | 手机/网上值机 | Kiosk 自助 | 人工柜台 |
|---|---|---|---|
| 前台设备归属 | 旅客自有设备 | 机场 CUSS | 机场 CUPPS 工作站 |
| 接入方式 | 航司 App/Web 直连 | CUSS 平台加载航司应用 | CUPPS 平台登录航司应用 |
| 后台系统 | 航司 DCS | 航司 DCS | 航司 DCS |
| 机场资源占用 | 0 | 1 台自助机 × ~90 秒 | 1 个柜台 × ~150 秒 + 人力 |
| 能处理的异常 | 少（常规值机） | 中（选座、改座、打印行李牌） | 多（超售、特服、超规行李、改签、证件复核） |
| 触发报文 | 同 | 同 | 同（+ 更多人工判断） |

**托运二分支对比**

| | 自助托运 SBD | 柜台托运 |
|---|---|---|
| 称重/量方 | 设备自动 | 人工 + 电子秤 |
| 行李牌 | 旅客自贴（两步式：先在 Kiosk 打牌） | 员工贴 |
| 证据链（Res 753 节点①） | 自动读码生成 | 员工扫码生成 |
| 超规处理 | 无法处理 → 引导至柜台 | 现场处理（超重收费 / 特殊行李通道） |
| 平均耗时 | 约 45–60 秒 | 约 90–150 秒 |
| 共同点 | **都由航司 DCS 生成 BSM，行李数据身份完全一致** | 同 |

## 12. 技术架构

### 12.1 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 3D 引擎 | **Three.js r0.169（ES Module + importmap）** | 与 airport-twin / elevator-twin 一致，CDN 直载、免构建 |

| 部署 | 静态文件，Nginx + Cloudflare | 与现有站点一致 |

### 12.3 关键技术约束（来自既有项目的经验）

1. **必须用 importmap + `type="module"`**，禁止 `examples/js/` 旧路径（r149 后已删除，会导致白屏）。
2. **CSS2DObject 的 `position` 只读**，必须 `.position.set()`，不可 `Object.assign`。
3. **动画用 rAF，逻辑用 `setInterval`**：后台标签页 rAF 会被节流到 ~1fps，逻辑推进要独立。
4. **发版打版本戳**：Cloudflare 边缘会覆盖源站 no-cache，需给所有本地模块 URL 加 `?v=<版本>`，避免新旧混装。
5. **左右镜像的几何体不能用 `scale.x = -1`**（法线翻转导致光照异常），需按符号分别建几何。

## 14. 验收标准、风险与扩展

### 14.1 教学验收（Demo 完成后自测）

| # | 问题 | Demo 中应能指出的答案位置 |
|---|---|---|
| 1 | 值机自助机是谁的设备、跑谁的系统？ | S3 分支卡 + `cuss`/`dcs` 知识卡 |
| 2 | 行李何时在系统中"出生"？ | S4 的 BSM 报文动画与卡片 |
| 3 | 为什么旅客不登机就必须卸行李？ | S9 的 No-show → BUM 事件分支 |
| 4 | TOBT 与 TSAT 分别谁定？ | S10 的 A-CDM 里程碑条 |
| 5 | 机场并列管着哪些域？ | 右侧管理域地图（常驻） |
| 6 | AODB 与 DCS 的数据边界？ | 底部链路条中"旅客数 vs 旅客姓名"的对比注释 |

### 14.2 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 3D 内容量过大导致首屏慢 | 体验差 | 全程序化建模（无外部 GLTF），按幕懒加载场景 |
| 信息密度过高，学习者过载 | 教学失效 | 默认只显示 3 条关键信息，专家细节收在卡片里 |
| 术语中英混杂 | 阅读负担 | 首次出现给全称 + 缩写 + 中文，之后统一用缩写并可悬停查看 |
| 各机场/航司实践差异大 | 被质疑不准确 | 卡片标注"通用做法 / 区域差异（欧洲 / 中国 / 北美）" |
| 移动端三栏拥挤 | 可用性 | 移动端改为"3D 全屏 + 底部抽屉切换三个面板" |

### 14.3 后续扩展方向

1. **到达侧旅程**：落地 → 摆渡/廊桥 → 边检 → 行李提取（转盘分配、Res 753 节点④）→ 海关 → 陆侧离场。
2. **中转旅程**：MCT（最短衔接时间）、行李中转 BTM、误机保护。
3. **不正常航班**：延误/取消/备降下的旅客再保护、行李追回、机位与登机口重排（可直接复用 airport-twin 的 RMS/DMAN 逻辑）。
4. **与 airport-twin 打通**：本 Demo 的第 10 幕结束处，正是 airport-twin 的开始（过站与飞行区），形成"旅客视角 → 运行视角"的双联展示。
5. **考核模式**：走完流程后随机出题，按知识卡覆盖度评分，形成可用于企业内训的轻量 LMS。
